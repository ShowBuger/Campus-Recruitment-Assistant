# 共享岗位 AI 去重

只根据输入记录判断，不补充外部事实。目标是避免重复招聘入口，同时避免误删不同岗位或不同投递渠道。

## 判断流程

逐个处理候选记录及其相似的现有记录：

1. **首先确认招聘批次必须兼容。** 优先比较 `normalized_batch`：
   - `秋招` 与 `2027:秋招` 兼容，因为部分来源省略届别；
   - 两边都明确写出年份且年份不同，视为不同招聘活动，严禁判为重复；
   - 秋招、提前批、春招、实习属于不同阶段，严禁跨阶段判重。
2. 确认公司名称是否指向同一主体或同一招聘品牌。忽略常见公司后缀、空格、大小写及括号内地域信息。
3. 比较岗位覆盖范围：
   - 岗位名称不同但都是同一批次的综合岗位集合、岗位大类或同一招聘项目，倾向进行合并。
4. **当公司名称相似时，以下情况高度倾向判为重复，即使岗位名称不同：**
   - `normalized_url` 完全相同，属于同一招聘入口，应当合并。
   - 链接指向相同域名（域名相同、路径前缀相近的，如 `/campus` 与 `/campus/2027`），且岗位覆盖范围接近时，倾向合并。
   - **一方有链接、另一方无链接：公司相同时倾向判为重复。** 不同来源可能只有部分来源提供了投递链接，缺失链接不代表是不同的招聘机会，应当合并。
   - 同一公司的校招官网，不同来源可能用不同岗位描述（如"2027届校招"vs"秋招正式批"），不影响同一招聘项目的判断。
5. 比较投递入口的其他情况：
   - 链接不同不等于记录不同，可能是同一招聘项目的详情页、跳转页或镜像入口。
   - 链接域名不同、或域名相同但路径前缀完全不同（如 `/campus` vs `/social`）时，不应仅凭公司相似判为重复。
6. 只有证据足以说明候选已被现有记录覆盖时，才设置 `duplicate=true` 和 `should_add=false`。
7. 信息不足或无法可靠判断时，设置 `duplicate=false` 和 `should_add=true`，防止误删。

## 输入

输入是 JSON 数组。每项包含：

- `candidate_id`：候选记录标识。
- `candidate`：待新增记录，含公司、原始批次、规范批次、岗位、原始链接、规范链接、链接域名、城市和方向。
- `similar_records`：公司相似且批次一致的现有或本批次已保留记录。

## 输出

只输出 JSON 数组，不要输出 Markdown 或解释性前缀。每个候选必须且只能返回一项：

```json
[
  {
    "candidate_id": "candidate-1",
    "duplicate": true,
    "should_add": false,
    "matched_record_id": "shr123",
    "reason": "同一公司同一秋招项目，岗位集合已被现有记录覆盖"
  }
]
```

约束：

- **明确年份不同或招聘阶段不同的记录严禁判为重复，即使公司相同、链接相同。**
- `candidate_id` 必须与输入一致。
- `duplicate` 与 `should_add` 必须互为相反值。
- `matched_record_id` 仅在重复时填写；否则为空字符串。
- `reason` 使用不超过 40 个汉字说明关键依据。
